# Numbat API Reference for GoSrcCtrl Enhancements

## Overview of Numbat and Sourcetrail Integration  
Numbat is a Python SDK for creating and manipulating Sourcetrail database files ([GitHub - quarkslab/numbat: Library to manipulate and create Sourcetrail databases](https://github.com/quarkslab/numbat#:~:text=Numbat%20is%20an%20API%20to,easily)). Sourcetrail is a source code exploration tool that visualizes symbols (classes, functions, etc.) and their relationships. Numbat allows you to **programmatically index arbitrary code relationships** into a Sourcetrail DB, which can then be opened in the Sourcetrail UI ([Leveraging Sourcetrail to a mapping tool, meet Numbat and Pyrrha - Quarkslab's blog](https://blog.quarkslab.com/leveraging-sourcetrail-to-a-mapping-tool-meet-numbat-and-pyrrha.html#:~:text=Let%E2%80%99s%20meet%20Numbat)). This makes it possible to extend Sourcetrail’s capabilities to new languages or data (for example, using Numbat to index Go code via the GoSrcCtrl tool). The typical workflow with Numbat is straightforward: **(1)** open or create a database, **(2)** record symbol nodes (e.g. classes, structs, functions), and **(3)** record relationships (edges) between those symbols ([Leveraging Sourcetrail to a mapping tool, meet Numbat and Pyrrha - Quarkslab's blog](https://blog.quarkslab.com/leveraging-sourcetrail-to-a-mapping-tool-meet-numbat-and-pyrrha.html#:~:text=1,Create%20relationships%20between%20nodes)). After adding all data, you call `db.commit()` and `db.close()` to write out the `.srctrldb` database and a corresponding project file ([Tutorial - Numbat Documentation](https://quarkslab.github.io/numbat/tutorial/#:~:text=db%20%3D%20SourcetrailDB.open%28Path%28%27my_database%27%29%2C%20clear%3DTrue%29%20,close)).

**Basic Usage Example:** The snippet below (from the official documentation) creates two class symbols and a field usage relationship between them ([GitHub - quarkslab/numbat: Library to manipulate and create Sourcetrail databases](https://github.com/quarkslab/numbat#:~:text=,parent_id%3Dmy_main)). It opens a new database, inserts a class with a method, another class with a field, then records that the method *uses* the field, before committing the changes: ([GitHub - quarkslab/numbat: Library to manipulate and create Sourcetrail databases](https://github.com/quarkslab/numbat#:~:text=from%20pathlib%20import%20Path%20from,numbat%20import%20SourcetrailDB)) ([GitHub - quarkslab/numbat: Library to manipulate and create Sourcetrail databases](https://github.com/quarkslab/numbat#:~:text=,parent_id%3Dclass_id))

```python
from pathlib import Path
from numbat import SourcetrailDB

db = SourcetrailDB.open(Path('my_db'), clear=True)

# Create a first class containing the method 'main'
my_main = db.record_class(name="MyMainClass")
meth_id = db.record_method(name="main", parent_id=my_main)

# Create a second class with a public field 'first_name'
class_id = db.record_class(name="PersonalInfo")
field_id = db.record_field(name="first_name", parent_id=class_id)

# The method 'main' is using the 'first_name' field
db.record_ref_usage(meth_id, field_id)

db.commit()
db.close()
``` 

In Sourcetrail, this produces a graph showing the two class nodes with a **“use”** reference from the `main` method to the `first_name` field ([Leveraging Sourcetrail to a mapping tool, meet Numbat and Pyrrha - Quarkslab's blog](https://blog.quarkslab.com/leveraging-sourcetrail-to-a-mapping-tool-meet-numbat-and-pyrrha.html#:~:text=After%20running%20this%20code%2C%20opening,will%20produce%20the%20following%20result)):  

 ([Leveraging Sourcetrail to a mapping tool, meet Numbat and Pyrrha - Quarkslab's blog](https://blog.quarkslab.com/leveraging-sourcetrail-to-a-mapping-tool-meet-numbat-and-pyrrha.html)) *Sourcetrail visualization of a usage reference: method `main` (in `MyMainClass`) **uses** the field `first_name` (in `PersonalInfo`) ([Leveraging Sourcetrail to a mapping tool, meet Numbat and Pyrrha - Quarkslab's blog](https://blog.quarkslab.com/leveraging-sourcetrail-to-a-mapping-tool-meet-numbat-and-pyrrha.html#:~:text=After%20running%20this%20code%2C%20opening,will%20produce%20the%20following%20result)).*  

## Recording Symbols and Hierarchies (Classes, Structs, Fields, etc.)  
Numbat provides high-level functions to record various **symbol nodes** in the database. All symbol-recording methods share a similar signature: `record_<type>(name="", prefix="", postfix="", delimiter=..., parent_id=None, is_indexed=True, hover_display="")` ([Tutorial - Numbat Documentation](https://quarkslab.github.io/numbat/tutorial/#:~:text=,show%20as%20a%20grey%20shadow)). The `name` is the symbol’s identifier, while `prefix`/`postfix` allow adding qualifiers around the name (e.g. type signatures). The `parent_id` parameter is crucial for **hierarchy**: it lets you nest symbols within others (for example, a field inside a struct, or a method inside a class) ([Tutorial - Numbat Documentation](https://quarkslab.github.io/numbat/tutorial/#:~:text=,show%20as%20a%20grey%20shadow)). By using `parent_id`, Numbat will form a qualified name with a delimiter (default `::`) to reflect containment (the delimiter can be changed to `/`, `.`, etc. as needed) ([Tutorial - Numbat Documentation](https://quarkslab.github.io/numbat/tutorial/#:~:text=,show%20as%20a%20grey%20shadow)). Set `is_indexed=True` for real symbols from source (as opposed to “inferred” or missing symbols, which would appear greyed-out in Sourcetrail). Below are commonly used symbol recording functions, with their intended use:

- **`record_class(...)`** – Creates a class node in the DB ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_class%28%20name%3D,)). You can supply an optional `prefix`/`postfix` for things like `class` keywords or trailing symbols, but these can usually be left empty. This returns an integer ID for the new class node ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=Type%20Description%20%60int%20)). If the class is inside a namespace or package, pass the container’s ID via `parent_id` (alternatively, use `record_namespace`/`record_package` for top-level grouping).  
- **`record_struct(...)`** – Similar to `record_class`, but marks the node as a **struct** type ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=,23)). Use this for Go structs if you want them categorized differently in the UI (Sourcetrail’s schema distinguishes class vs struct nodes). The parameters are the same as for class.  
- **`record_interface(...)`** – Records an **interface/trait** node ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_interface)). In languages like Go, you can use this for Go interfaces. Like classes, it returns an ID. (Go’s interfaces can also be treated as classes in terms of relationships – see **Inheritance and Implementation** below.)  
- **`record_field(...)`** – Records a **field/member variable** symbol ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_field%28%20name%3D,)). Typically you’ll call `record_field(name="fieldName", parent_id=<struct_or_class_id>)` to attach the field to its containing struct/class ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=)). This ensures the field is shown under that type’s hierarchy. The returned ID is the field’s node ID. (Internally, the parent link also means the field’s full name will include the parent’s name with a delimiter.)  
- **`record_method(...)`** – Records a **method** defined inside a class ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_method%28%20name%3D,)). Use `parent_id=<class_id>` to link it to its class. For Go, methods on struct types can be represented this way (with the struct type as parent). If you need to record a free-standing function (not tied to a type), use `record_function(...)` instead ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_function%28%20name%3D,)) (same signature but without a parent). Both return a new symbol ID.  

Numbat also supports other symbol types (globals, enums, macros, etc. – see full API docs ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=,record_type_parameter_node))), but the above are most relevant for structuring Go code in Sourcetrail. You can also create higher-level containers: e.g. `record_namespace("mypkg")` or `record_package("mypkg")` to represent a Go package or module ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=,23)). Then you might use that package’s ID as the parent for all top-level functions or types in that package, to group them. In summary, by using `parent_id` relationships appropriately, you can **nest symbols** so that fields appear under their struct, methods under their receiver type, and types under packages, mirroring Go’s symbol hierarchy in the Sourcetrail DB.

## Recording Different Reference Types (Edges: Usage vs Call, Inheritance, Imports, etc.)  
Once nodes are recorded, you can create directed **reference edges** between them to represent relationships. Numbat’s API has specialized `record_ref_*` methods for each kind of relationship Sourcetrail supports ([Tutorial - Numbat Documentation](https://quarkslab.github.io/numbat/tutorial/#:~:text=Relationships)) ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=,record_ref_include)). This lets you differentiate calls vs uses, inheritance vs implementation, and so on. Each `record_ref_X(source_id, dest_id, hover_display='')` returns an integer reference ID for the new edge ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=Returns%3A)) ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=)). The `hover_display` is an optional text label shown on the edge when hovered in the UI (you can use this to annotate an edge, e.g. label an interface implementation as “implements”) ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=required%20)). Key reference types include:

- **Usage References:** `record_ref_usage(src, dest)` – Denotes a generic **usage** of one symbol by another ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_ref_usage)). For example, if a function or method *accesses or uses* a variable, field, or calls a function in a non-call context (like passing it as an argument or referencing it), you can model it as a usage edge. In the example above, we recorded that the `main` method *uses* the `first_name` field via `record_ref_usage(meth_id, field_id)` ([Tutorial - Numbat Documentation](https://quarkslab.github.io/numbat/tutorial/#:~:text=class_id%20%3D%20db.record_class%28prefix%3D,record_ref_usage%28meth_id%2C%20field_id)) ([Tutorial - Numbat Documentation](https://quarkslab.github.io/numbat/tutorial/#:~:text=)). Sourcetrail will display this as a directed arrow (with a small “use” tag) from the source to the target symbol.  
- **Call References:** `record_ref_call(src, dest)` – Marks a **function call** relationship ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_ref_call)). Use this when one function invokes another. For instance, if function `A` calls function `B`, you would do `db.record_ref_call(A_id, B_id)`. This creates a distinct edge labeled as a call in Sourcetrail (often highlighted differently). Numbat allows you to differentiate calls from mere usages, which is important for building an accurate call graph.  
- **Inheritance / Implementation:** `record_ref_inheritance(subtype_id, supertype_id)` – Adds an **inheritance** edge (also used for interface implementation) ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_ref_inheritance)). If you have a class `C` that extends class `Base`, or a struct that implements an interface, use `record_ref_inheritance(C_id, Base_id)`. In the context of Go, since there’s no explicit subclassing, you would mainly use this for representing a struct implementing an interface. For example, given an interface node and a struct node, linking them with `record_ref_inheritance(struct_id, interface_id)` will indicate the “implements” relationship (in the UI it will appear as a generalization/specialization link). There’s also `record_ref_override` for an overriding method relationship ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_ref_override)) (useful in class hierarchies if a method in a subclass overrides one in a base class).  
- **Type Usage:** `record_ref_type_usage(src, dest)` – Represents one symbol using another *as a type* ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_ref_type_usage)). This is handy if, for example, a variable or field of type `T` is declared in function `F` – you could connect `F` to the type node `T` via a type usage edge. (This might be relevant for Go if you want to show that a variable uses a struct type or an interface as its type.)  
- **Membership:** `record_ref_member(parent, child)` – An explicit **member-of** relationship ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_ref_member)). Normally, if you created a field with `parent_id` linking it to a struct, Sourcetrail’s UI will inherently show that as a member. But you can also record a member reference to explicitly denote that relationship. The edge table in Sourcetrail is used to indicate membership (e.g. “field *f* is member of class *C*”) as well as other relations ([numbat/src/numbat/types.py at main · quarkslab/numbat · GitHub](https://github.com/quarkslab/numbat/blob/main/src/numbat/types.py#:~:text=The%20%27edge%27%20table%20is%20used,between%20element%20of%20the%20%27node)). In practice, using `parent_id` when creating the field may be sufficient to model containment; `record_ref_member` is available if you need an actual edge in the graph view connecting the two nodes (Sourcetrail may or may not visualize an explicit member edge depending on context).  
- **Import/Include Relations:** If you want to capture module imports or file inclusions (to visualize dependencies between files or packages), Numbat provides:  
  - `record_ref_import(src, dest)` – for a high-level **import** relationship ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=)). Here `src` would be the entity that imports, and `dest` the thing being imported ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=)). For example, if package A imports package B, record_ref_import(A_id, B_id) will create an edge (often shown as “import” in the UI).  
  - `record_ref_include(src, dest)` – for C/C++ style **include** directives ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_ref_include)), where `src` is typically a file that includes another file (header). In Go you likely won’t use `include`, just `import`.  
- **Other Reference Types:** Sourcetrail (and Numbat) define a few more edge types, such as template specialization, macro usage, and annotation usage ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_ref_macro_usage)) ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_ref_annotation_usage)), which are more relevant to C++ or Java. For completeness, Numbat exposes `record_ref_template_specialization`, `record_ref_macro_usage`, `record_ref_annotation_usage`, etc., each adding the corresponding edge. Most of these won’t apply to Go code, but they illustrate that the API covers a wide range of relationships.

Each of these `record_ref_*` calls returns an edge (reference) ID that you can later use to attach source locations (discussed next). **Direction matters**: the `source_id` and `dest_id` you pass define the arrow direction. For example, in `record_ref_call(src, dest)`, `src` is the caller and `dest` is the callee ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=)). In `record_ref_import`, `src` is “who imports” and `dest` is “what is imported” ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=)). If unsure, you can refer to the docstring which often clarifies the roles. Also note the `hover_display` parameter in all these functions – you can use it to customize the edge’s tooltip text ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=required%20)). For instance, you might do `db.record_ref_inheritance(struct_id, interface_id, hover_display="implements")` to make the UI show “implements” when hovering that inheritance edge, giving more context.

## Capturing Source Locations (Definitions and References in Code)  
One powerful feature Numbat offers is the ability to link the abstract symbols and references to **physical source code locations** in files. This enables Sourcetrail’s source viewer and “go to definition”/“find usages” features. To use this, you first need to **record the source file** itself in the database:

- **`record_file(path)`** – Adds a file entry to the DB for the given file path ([Tutorial - Numbat Documentation](https://quarkslab.github.io/numbat/tutorial/#:~:text=,parent_id%3Dclass_id)). It returns a file ID. You should do this for each source file you want to associate with your symbols.  
- **`record_file_language(file_id, lang)`** – Optionally tag the file with a language (e.g. `"python"`, `"cpp"`, etc.) ([Tutorial - Numbat Documentation](https://quarkslab.github.io/numbat/tutorial/#:~:text=,parent_id%3Dclass_id)). Sourcetrail uses this for syntax highlighting. If Go is not officially recognized, you might use a closest match (or simply omit this; unrecognized language might default to plain text). 

Once files are in the DB, you can attach location info: 

- **`record_symbol_location(symbol_id, file_id, start_line, start_column, end_line, end_column)`** – Records the precise location of a symbol’s name in the source code ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_symbol_location)) ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=Name%20Type%20Description%20Default%20,int)). For example, after recording a function symbol, call this with the coordinates of that function’s definition (the span of the name in the source file). This lets Sourcetrail highlight where the symbol is defined. You can call this multiple times if a symbol has multiple declarations/definitions (though for Go typically one definition). There are related variants: `record_symbol_signature_location` to mark the span of a function’s signature (if you want the entire signature highlighted) ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_symbol_signature_location)), and `record_symbol_scope_location` to mark the extent of a symbol’s scope/block ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_symbol_scope_location)) (e.g. the body of a function from “{” to “}”). Marking scope is useful so that Sourcetrail knows the range of lines that belong to that function, enabling features like showing the whole function body in the UI when the node is selected.  
- **`record_reference_location(reference_id, file_id, start_line, start_column, end_line, end_column)`** – Records an occurrence of a previously created reference edge in the source code ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_reference_location)) ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=Name%20Type%20Description%20Default%20,int)). For example, if you recorded a `record_ref_call(A, B)` to denote a call from function A to B, you should also record where that call happens in code: use the returned reference ID and provide the location of the call site in file (A’s file, at the line/column where B is called). This enables Sourcetrail’s “find references” and allows clicking the usage to jump to that line in the source viewer. **Important:** For each `record_ref_*` edge you add, you should call `record_reference_location` at least once (possibly multiple times if the same reference happens in multiple places) so that the DB knows where that relationship is manifested in code. If you omit this, the graph will still show the relationship, but the source panel won’t list any concrete occurrence for it.  
- **`record_local_symbol(name)`** and `record_local_symbol_location(...)` – These allow recording local (non-global) variables or symbols that aren’t added as full nodes in the graph ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_local_symbol)) ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=The%20identifier%20of%20the%20new,local%20symbol)). For instance, if you want to highlight a local variable’s usage in the source viewer, you can record it as a “local symbol” (which doesn’t appear in the graph’s symbol index but can have locations). This is an advanced feature; for the purposes of GoSrcCtrl, you might not need to explicitly record all local variables unless you want them clickable in the Sourcetrail UI.  

By using the above location APIs, you can ensure the Sourcetrail database is fully synchronized with the original source code: each symbol knows where it’s defined, and each relationship knows where it occurs. GoSrcCtrl can use `record_symbol_location` for every definition (functions, struct types, interface types, fields, etc.) and `record_reference_location` for every usage or call it indexes, enabling Sourcetrail’s UI to show “Go to Definition” and “Go to Usage” links for Go code just like it does for C++/Java.

## Extending Numbat for Additional Needs  
**Numbat already supports all major Sourcetrail relationship types**, so many of GoSrcCtrl’s planned enhancements (distinguishing call vs usage, struct field containment, interface implementation, import dependencies, etc.) can be accomplished with the existing API as shown above. For example, the ability to tag function calls separately from variable usages is provided out-of-the-box via `record_ref_call` vs `record_ref_usage` ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_ref_call)) ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=record_ref_usage)). If you find a concept that isn’t directly supported, there are a few ways to adapt: 

- **Use existing categories with custom labels or context.** Since the Sourcetrail schema has a fixed set of edge types, you might map a new concept to one of those. For instance, Go’s embedded struct could be modeled as an inheritance edge (even though it’s not inheritance semantically) so that you get a visual link between the struct and the embedded field. You could then set a `hover_display` like “embeds” to differentiate it from a regular inheritance ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=required%20)). This leverages the fact that Numbat’s `EdgeType` enum includes all these relationships (e.g. `EdgeType.INHERITANCE`) and the UI will recognize it ([numbat/src/numbat/types.py at main · quarkslab/numbat · GitHub](https://github.com/quarkslab/numbat/blob/main/src/numbat/types.py#:~:text=CALL%20%3D%201%20)) ([numbat/src/numbat/types.py at main · quarkslab/numbat · GitHub](https://github.com/quarkslab/numbat/blob/main/src/numbat/types.py#:~:text=INHERITANCE%20%3D%201%20)). Using a custom hover text or even color (`change_edge_color`) can convey the nuance without needing a new fundamental type. 
- **Contribute or fork if necessary.** Numbat is open-source, and its implementation (in pure Python) is designed to be extensible. The public API functions map to internal database operations defined in Numbat’s code (for example, each `record_ref_*` corresponds to inserting an edge with a specific type code in the underlying SQLite DB). If a truly new relationship type or feature is needed that Sourcetrail’s original schema doesn’t cover, you would have to modify the `EdgeType` definitions in Numbat’s `types.py` and possibly adjust the UI. Quarkslab has also created **NumbatUI**, a custom fork of the Sourcetrail viewer, to support some extended features (like custom node types and colors) ([Customization - Numbat Documentation](https://quarkslab.github.io/numbat/customization/#:~:text=Warning)) ([Customization - Numbat Documentation](https://quarkslab.github.io/numbat/customization/#:~:text=These%20features%20can%20only%20be,in%20progress%20and%20really%20unstable)). For the most part, if you stay within the provided types (class, struct, interface, etc., and edges like call, usage, import, inheritance), the standard Sourcetrail UI will display them correctly. If you need to go beyond (say, define a new edge category), you might coordinate with the Numbat maintainers via a contribution, or maintain a fork along with using NumbatUI for visualization. The **“Numbat Internal Dev”** docs and the source code are good references for understanding how the API functions correspond to DB schema operations (for example, the edge table schema is shown in the source comments ([numbat/src/numbat/types.py at main · quarkslab/numbat · GitHub](https://github.com/quarkslab/numbat/blob/main/src/numbat/types.py#:~:text=)) ([numbat/src/numbat/types.py at main · quarkslab/numbat · GitHub](https://github.com/quarkslab/numbat/blob/main/src/numbat/types.py#:~:text=The%20%27edge%27%20table%20is%20used,between%20element%20of%20the%20%27node))). 

In summary, Numbat provides a rich API to cover the relationships needed for GoSrcCtrl’s roadmap. By using `record_class/struct/interface` with parent IDs, you can structure Go types and their fields hierarchically. By using `record_ref_call` vs `record_ref_usage`, you can accurately distinguish function calls from generic references. `record_ref_inheritance` will let you link interfaces to structs that implement them (or even denote embedded struct relationships). `record_ref_import` captures package import dependencies. And by diligently recording locations with `record_symbol_location` and `record_reference_location`, the resulting Sourcetrail DB will allow users to navigate definitions and references in the Go codebase with ease. All of these capabilities are supported by Numbat’s current API ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=,record_ref_include)) ([Public API Reference - Numbat Documentation](https://quarkslab.github.io/numbat/public_api/#numbat.SourcetrailDB.record_ref_member#:~:text=Returns%3A)), so GoSrcCtrl’s enhancements can be implemented largely by leveraging these existing functions. If any gap is encountered, Numbat’s extensible design and open codebase provide a path to extend the functionality either through configuration or code contributions, ensuring a comprehensive and correct Sourcetrail database for Go.
